# ADPCM-B 再生時の実機仕様

`$00` に `$A0` / `$B0` を書いて外部メモリから再生するときの実機仕様をまとめる。
CPU からの外部メモリ read/write は [04_data-register.md](04_data-register.md) が扱う。

この章は **[実測] の比率が高い**。フェッチ周期・EOS の位置・ラッチ列の共有は、
いずれもロジックアナライザで実チップから直接測っている。
根拠ラベルの意味は [01_overview.md](01_overview.md) を参照。

---

## 1. 再生の設定手順

| 順 | レジスタ | 値 | 意味 |
|---|---|---|---|
| 1 | `$10` | `$00` → `$80` | IRQ フラグのリセット (EOS / BRDY をクリア) |
| 2 | `$00` | `$20` | いったん MEMDATA=1 / START=0 にする (前の再生を止める) |
| 3 | `$01` | 例: `$C2` | L/R 出力 ON + ×8bit DRAM |
| 4 | `$02` / `$03` | START | 開始アドレス。**32 バイト単位のブロック番号** |
| 5 | `$04` / `$05` | STOP | 終了アドレス。**このブロックの終わりまで**再生する |
| 6 | `$09` / `$0A` | ΔN | 再生レート |
| 7 | `$0B` | LEVEL | 音量 |
| 8 | `$00` | `$A0` / `$B0` | START=1 (REPEAT なら `$B0`) で再生開始 |

LIMIT (`$0C` / `$0D`) は再生ごとに設定する必要はない。使わないなら `$FFFF` にしておく。

時間換算は [02_internals.md](02_internals.md) §8 を参照。以下は ΔN = 512 の値で示す
(1 ニブル = 2.3077ms、1 バイト = 4.6154ms)。

## 2. メモリフェッチの周期と回数 [実測]

外部メモリのイネーブル信号を 1 アクセスずつ数えると、1 回の再生は次のようになる。

```
時刻 (ms)     アクセス
  0.000        2 回     <- 開始直後のバースト (2 バイト先読み)
  2.33         1 回     <- 1 ニブル後に 3 バイト目
  6.94         1 回     ┐
 11.56         1 回     ├ 以後 4.6154ms (= 2 ニブル) 周期でちょうど 1 回ずつ
  ...                   ┘
136.17         1 回     <- 最後のフェッチ
```

- **開始直後に 2 バイトを先読みする。** 1 サンプル区間 (18us) 内に 2 回のアクセスが入る。
- **その 1 ニブル後に 3 バイト目**をフェッチする。
- **以後は 2 ニブルごとに 1 バイト。**
- **32 バイトブロックのフェッチ総数はちょうど 32 回。**

先読みの深さは 1 バイト固定である [解析]。L1 / L2 は常に「現在デコード中のバイトの
ちょうど 1 バイト先」を保持し、L4 が現在デコード中のバイト、
**L3 はそれを渡す直前のステージング段として 1 バイト先を保持する**。
外部フェッチは、そのバイトの **1 ニブル目をデコードした直後**に走る。

## 3. EOS は再生開始から 61 ニブル後に立つ [実測]

同じ再生で EOS が 0 → 1 になるのは、**再生開始から 140.79ms 後**である。

```
61 ニブル / 433.33Hz = 140.77 ms   <- 一致
64 ニブル / 433.33Hz = 147.69 ms   <- 不一致
```

つまり **EOS は再生開始から 61 ニブルぶん後**に立つ。32 バイト = 64 ニブルの
ブロックを再生しても、64 ニブル分の時間が経つ前に EOS が立つ。

> **注意: 「EOS が立つ時刻」と「実際に何ニブルがデコードされたか」は別の量である。**
> 実機で外から観測できるのは前者だけで、内部で何ニブル消費されたかは直接には見えない。
> エミュレータを実機と比べるときは、この 2 つを混同しないこと。

## 4. 失われるのは常に末尾 1 バイト (2 ニブル)

再生範囲の最後の 1 バイトは、チップ内部まで取り込まれるが**デコーダへ送り出されない** [解析]。

これは **ブロック長・ΔN・メモリ種別のいずれにも依存しない**。
ブロック長 {32, 64, 96} バイト × ΔN {最大, 0x8000, 0x1000} × メモリ種別
{×8bit DRAM, ×1bit DRAM} の全 18 条件で、
「総ニブル数 − 供給ニブル数」は厳密に 2 (= 1 バイト) だった。

EOS の瞬間には L1〜L4 のすべてに最終バイトが到達済みで、
バイト自体は取り込み終えている。**それを抽出パルスとして送り出す最後の一歩だけが
EOS で止まる**という構造である。

ニブルの抽出は常に上位 4bit から行われ、下位ニブル専用の抽出回路は存在しない [解析]。
新しいバイトをロードした直後はその上位 4bit を取り、その後 1bit ずつ左シフトして
下位ニブルを上位へ持ち上げてから再び上位 4bit を取る。

## 5. 再生経路と CPU 経路はラッチ列を共有している [実測]

「再生 → 停止 → メモリ READ」を、待ち時間を変えながら繰り返し、
READ 冒頭のダミーリード 2 バイトを記録すると:

```
READ 0 : 2A, 2B, ...
READ 1 : 2D, 2E, ...
READ 3 : 31, 32, ...
READ 15: 4C, 4D, ...
```

- **ダミーリードの 2 バイトは必ず連番になる。**
- **待ち時間を伸ばすほど値が進む。**

メモリには連番を書いてあるので、**この 2 バイトは「再生が最後にフェッチした 2 バイト」**である。
つまり **再生用のフェッチと CPU の `$08` リードは同じラッチ列を通っている。**

同じ結論は、再生の直後に READ を始めたときのダミーリードにも現れる
([04_data-register.md](04_data-register.md) §4)。

## 6. 再生中の `$08` アクセス

### 6.1 read はメモリの内容を返す [実測]

**再生中に `$08` を読むと、再生用にフェッチ中の生バイトがそのまま返る。**

- 読める値は**メモリに書いた値そのもの**である。
  再生範囲に実在する値しか出てこない。無音パターン (`0x80` のみ) の再生中は毎回 `0x80` になる。
- 連続して読むと、**再生の進行に合わせて値が進んでいく**。
- **ニブルが入れ替わって読めることは無い** (バイト境界は保たれる)。

`$08` の read 経路はモードに関係なく常時有効で、L2 → L3 の転送も再生中は
デコーダ側の要求で自律的に進むためである [解析]。

### 6.2 write はメモリにもデコーダにも届かない [解析]

START=1 の状態では、データ源のセレクタが CPU 側 (L3) を切り離してエンコーダ側に切り替える。
`$08` へ書いてもメモリ内容は変化しない。ステータスから見て再生も止まらない [実測]。

### 6.3 BRDY への影響 [実測]

**メモリ駆動再生中の BRDY は常時 1 に張り付く。**
開始から EOS 後まで一度も 0 にならない。CPU を介さないメモリ駆動再生では、
BRDY は事実上意味を持たない。

ただし **再生中に CPU が `$08` に触れると BRDY は落ちる** (`0x28` → 以後 `0x20`)。

### 6.4 再生パイプラインからバイトを奪うか — **[未確定]**

**この論点だけは決着していない。**

[解析] では、**read / write のどちらでも再生パイプラインからちょうど 1 バイト (2 ニブル) を奪う。**
`$08` アクセスのトリガが read / write を区別せず先読み段を進めてしまうためである。
8 ニブルおきに 6 回注入すると、EOS が 62 → 50 ニブル (= 62 − 2×6) へ前倒しになり、
供給ニブル列から該当バイトが丸ごと欠落する。

一方 [実測] では、外部バスにその形跡が無い。

- 再生中に `$08` を 16 回 read / 16 回 write しても、
  **フェッチ周期 4.6154ms から 0.05ms 以上外れた間隔が 1 個も無い。**
- **1 ループあたりのフェッチ回数も増えない。**

ただしこれは「**奪ったぶんを補充するための再フェッチは起きない**」ことまでしか示さない。
「補充せずにラッチの内容を横取りするだけ」なら外部バスには現れないため、
**この観測だけでは [解析] の結果を否定できない。**

→ [09_open-questions.md](09_open-questions.md)

## 7. STOP 到達と LIMIT 到達の対比

| | STOP 到達 | LIMIT 到達 |
|---|---|---|
| 戻り先 | START アドレス | **0 番地** |
| EOS | **立つ** | **変化しない** |
| 出力レベル | 非 REPEAT = 保持 / REPEAT = 0 に戻して先頭から | **0 に戻らず継続** |
| ダミーリード (CPU 読み出し時) | 2 回 (REPEAT=1 なら 1 回) | **発生しない** |

- **判定は STOP が先。** LIMIT == STOP なら STOP 側の挙動になる。
- **どちらも一致比較であって大小比較ではない。**
- **LIMIT は EOS に一切つながらない。**

詳細は [03_address.md](03_address.md)。

## 8. REC / MEMDATA / REPEAT の組み合わせとステータス [実測]

`$00` の D6 (REC) / D5 (MEMDATA) / D4 (REPEAT) の全 8 通りについて、
`$08` の read 4 回・write 4 回でステータスを取った結果:

- 電源投入直後・リセット直後は `0x08` (BRDY=1)。
- **`$60` (REC=1, MEMDATA=1 = 書き込みモード) で `$08` を「読む」**と、
  2 回目以降 `0x00` になる (BRDY が落ちて張り付く)。`$70` (REPEAT 付き) も同じ。
- **`$20` (REC=0, MEMDATA=1 = 読み出しモード) で `$08` に「書く」**と、2 回目以降 `0x00` になる。
- それ以外の組み合わせは `0x08` のまま。

これは [04_data-register.md](04_data-register.md) §6 の
「REC ビットが転送方向のゲートとして効いている」と同じ現象である。

## 9. 停止シーケンス

| 操作 | 挙動 |
|---|---|
| `$00 <- $A1` (START を保ったまま RESET ビット) | 再生が止まり、出力レベルが変化しなくなる。**EOS が 0 でも 1 になる** |
| `$00 <- $00` | 出力レベルが 0 になり、**PCM BUSY が 0 になる**。EOS が 0 なら 1 に、BRDY が 0 なら 1 に強制される。ただし**再生開始後に `$10 <- $80` でクリアしてあれば、ここでは 1 にならない** |

PCM BUSY が 0 になるのは、`$00` に `$00` を書いたことで **START ビットが 0 になったから**であって、
再生が終わったからではない ([06_status-flags.md](06_status-flags.md))。
