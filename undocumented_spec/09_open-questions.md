# 未解決事項・今後の課題

決着していない論点を、**何が分かっているか / なぜ決着しないか / どうすれば決着するか**の
3 点セットで挙げる。

これらは本ドキュメント群の他の章に [未確定] または [推定] として現れる項目である。
根拠ラベルの意味は [01_overview.md](01_overview.md) を参照。

---

## 1. ZERO フラグの極性 — マニュアルと構造が逆

**分かっていること**

マニュアル p.52 は ZERO を「ADPCM 音声分析中、290msec 以上、**無音**状態が続く時 "1"」と
説明している。一方、構造どおりに読むと **無音の間はカウンタが 0 にリセットされ、
有音が継続したときにオーバーフローして立つ**という逆の論理になる。

カウンタ幅 (16384 FM サンプル ≒ 295ms) はマニュアルの 290msec と一致しており、
**こちらは信頼できる。** 食い違っているのは極性だけである。

**なぜ決着しないか**

考えられるのは 2 つで、どちらとも断定できない。

- マニュアルの日本語が誤解を招く書き方になっている
- 解析モデルの内蔵 A/D 変換部の極性が不正確 (この部分には既知の不確かさがある)

ZERO が有効なのは A/D 変換モード中だけなので、通常の再生では観測できない。

**どうすれば決着するか**

実機で A/D 変換モードを動かし、無音入力と有音入力それぞれで ZERO を観測する。

→ [06_status-flags.md](06_status-flags.md) §10、[07_manual-vs-hardware.md](07_manual-vs-hardware.md) #5

## 2. 再生中の `$08` アクセスが再生パイプラインからバイトを奪うか

**本ドキュメント群で最も重要な未決事項。**

**分かっていること**

- [解析] では、**read / write のどちらでも再生パイプラインからちょうど 1 バイト
  (2 ニブル) を奪う**。8 ニブルおきに 6 回注入すると、EOS が 62 → 50 ニブルへ前倒しになる。
  `$08` アクセスのトリガが read / write を区別せず先読み段を進めてしまうためである。
- [実測] では、外部バスにその形跡が無い。再生中に `$08` を 16 回 read / 16 回 write しても、
  **フェッチ周期が 0.05ms 以上乱れることは 1 度も無く、
  1 ループあたりのフェッチ回数も増えない。**

**なぜ決着しないか**

実測が示しているのは「**奪ったぶんを補充するための再フェッチは起きない**」ことまでである。
**「補充せずにラッチの内容を横取りするだけ」なら外部バスには一切現れない。**
したがって外部バス観測だけでは、解析側の結果を否定できない。

これは [01_overview.md](01_overview.md) に書いた「ロジックアナライザはアドレスバスを
観測していない」という測定系の限界がそのまま効いている例である。

**どうすれば決着するか**

- 再生出力の波形を、`$08` にアクセスした場合と対照実行で比較する
- `$08` を短周期で連打する実機テストを新規に取得する
  (現行の実機測定系は 1 アクセスあたり約 80ms かかるため、
  ニブル周期に対して十分密に叩けていない)

**エミュレータ実装への含み**: 決着するまでは、
「CPU 経路と再生経路が同じハンドシェイクを共有する」という構造を採るか、
再生中だけ例外を設けるかを決められない。前者は構造として自然だが、
実機で否定された場合は例外を入れることになり、構造の一貫性が部分的に崩れる。

→ [05_playback.md](05_playback.md) §6.4、[08_ymfm-differences.md](08_ymfm-differences.md) #14

## 3. ×1bit DRAM / ROM モードの実機での裏取りが無い

**分かっていること**

以下は [解析] で確認済みだが、**実機ログはすべて ×8bit DRAM の範囲**である。

- ×1bit DRAM のビット単位アドレッシング (1 バイトあたり 8 アクセス、LSB first)
- ROM の read が ×8bit DRAM と同じ byte 単位・同じダミーリード構造であること
- **ROM 指定時の書き込みが bit 単位になること**
- `$01 = $03` (ROM + ×8bit) がどの読み出し経路にも当たらないこと
- 実効アドレス幅が 21bit であること
- マスク中のフラグが破壊されること

**なぜ決着しないか**

実機測定に使えるハードウェア構成が ×8bit DRAM のみで、
1bit DRAM や ROM を接続した環境での測定が行われていない。

**どうすれば決着するか**

×1bit DRAM または ROM を接続した実機環境での測定。
実機でこれらを使うソフトウェア資産が見つかれば、そこからの追試も考えられる。

→ [03_address.md](03_address.md) §7

## 4. CPU 駆動モード (`$00 = $80`) の終了条件

**分かっていること**

`$80` (START=1, MEMDATA=0) の CPU 駆動再生では、外部メモリを使わず
CPU が `$08` へ書いたデータを直接デコードする。実機にはこのモード専用の
終了条件の経路が存在する [解析]。

**なぜ決着しないか**

このモードを使う実機測定がなく、**実機基準そのものが存在しない。**
外部メモリを使わないため、外部バス観測にも何も現れない。

**どうすれば決着するか**

`$80` モードで一定量のデータを流し、EOS の立つタイミングと
STOP / LIMIT の関与をステータスポーリングで観測する実機テストを新規に取得する。

→ [08_ymfm-differences.md](08_ymfm-differences.md) #15

## 5. REPEAT 時に EOS が保持されるという結論の留保

**分かっていること**

REPEAT 再生でも EOS は立てたまま保持され、自動クリアはされない [実測]。
4 ループ回した実測で一度も落ちなかった。

構造上は「REPEAT で EOS が再度発生したときにフラグをクリアする」経路が**書かれている**が、
その経路は到達しない。信号を受け渡す 2 つのクロックフェーズがずれており、
受け側がラッチする時点では送り側が既に 0 に戻っているためである。

**なぜ決着しないか**

上の結論は、**離散的な 2 相クロックモデルの上での帰結**である。
「論理としては書かれているのに到達しない」という経路は、
連続的な回路の挙動を離散フェーズへ落とし込む際に生じる**モデル化の副産物**である
可能性を完全には否定できない。

**どうすれば決着するか**

実機で REPEAT 再生中の EOS を高い時間分解能でポーリングする。
現行の測定系ではポーリング区間しか観測できないため、
EOS が短いパルスとして出ている可能性を排除しきれていない。

→ [06_status-flags.md](06_status-flags.md) §6

## 6. `START=0 / STOP=1 / LIMIT=0` という縮退設定

**分かっていること**

**前に別の再生を 1 度でも走らせた後に** `START=0 / STOP=1 / LIMIT=0` で再生を開始すると、
PCM BUSY は 1 になるのに**外部メモリフェッチが 1 回も走らない** [解析]。
同じレジスタ設定でも、その再生がリセット後の最初の 1 回であれば通常どおりフェッチする。

LIMIT = 0 は「折り返し先と LIMIT が同じ」という縮退条件である。

**なぜ決着しないか**

**この条件の実機ログが存在しない。**

**どうすれば決着するか**

この設定を実機で走らせ、外部メモリアクセスの有無を観測する。

→ [05_playback.md](05_playback.md) §7

## 7. ブロック境界での二重ディスパッチが実チップにもあるか

**分かっていること**

メモリ I/F シーケンサの DRAM リフレッシュ迂回と、STOP 到達直後の START 再ディスパッチが、
**特定の位相で噛み合うと二重に走る** [解析]。リフレッシュ迂回は約 92 マスタクロック周期で
反復し、そのうち約 2/92 の位相で発生する。

**時間の長短ではなく位相で決まる**ことは、複数の独立した観測で確認されている。

**なぜ決着しないか**

実機ログのブロック境界に相当する箇所 114 件で、異常はゼロだった。
2/92 ≈ 2.2% をそのまま当てはめると、114 件すべてが正常になる確率は約 8% である。
**「実チップにはこのレースが無い」側に傾いているが、断定できる母数ではない。**

このレースが解析モデル固有のものか、実チップにも存在するのかで、
エミュレータがブロック境界を特別扱いすべきかどうかが変わる。

**どうすれば決着するか**

**ブロック境界を数百回踏む実機テスト**を新規に取得する。
現行の実機ログは 1 シナリオあたり境界を数回しか通らないため、母数が足りない。

## 8. STATUS1 の D6 を駆動しているのが読み出しデータラッチであること [推定]

**分かっていること**

`$08` のメモリリード直後は D6 に直前に読み出したデータの bit6 が出るのに対し、
メモリライト後は D6 が常に 0 になる [実測]。この非対称は
**バス容量の残留 (フローティング) では説明できない** —
ライト時も直前にバスへ出ていたのは書き込みデータだからである。

**なぜ [推定] に留まるか**

「読み出しデータラッチが D6 を駆動している」というのは、
観測された非対称からの最も自然な説明であって、回路上の確認ではない。

**どうすれば決着するか**

チップのダイ解析、または D6 の値がどのラッチ段に追随するかを切り分ける実機テスト。

**ただし実用上の重要性は低い。** フラグとしての意味が無いため、
機構が何であれエミュレータの挙動は変わらない。

→ [06_status-flags.md](06_status-flags.md) §7

## 9. 優先度

実機測定の機会があるとき、決着させる価値が高い順:

| 順位 | 項目 | 理由 |
|---|---|---|
| 1 | **#2 再生中の `$08` アクセスの副作用** | エミュレータの構造設計そのものが決まらない。音にも直接影響する |
| 2 | **#3 ×1bit DRAM / ROM の裏取り** | 現在 [解析] 止まりの結論が広範囲にわたる。測定系を用意すれば一度に多くが確定する |
| 3 | **#7 ブロック境界の二重ディスパッチ** | 境界を多数踏むテストを 1 本取るだけで決着する |
| 4 | **#1 ZERO の極性** | マニュアルとの食い違いが残り続ける。ただし影響範囲は A/D 変換モードのみ |
| 5 | **#5 REPEAT 時の EOS 保持** | 結論自体は実測で得られており、留保を消すための追試 |
| 6 | **#4 CPU 駆動モードの終了条件 / #6 縮退設定** | 実際に使われる設定ではない |
| — | **#8 D6 の機構** | 実用上の影響が無い |
